Descripción
Registra en LDCOM uno o varios tipos de crédito (planes de financiamiento) con sus datos generales y sus plazos, para que Facturación y Preventa puedan ofrecerlos como forma de pago y calcular la simulación de cuotas.
El cuerpo es siempre una lista, aunque se envíe un solo tipo de crédito. Un registro que falla no detiene a los demás: se procesa el resto. La respuesta lista los que sí entraron; el detalle de los rechazados (posición en la lista y motivo) solo viene cuando no entra ninguno (500).
El endpoint registra el encabezado del tipo de crédito. La asociación de artículos y de clientes no forma parte del flujo normal: se hace después desde el mantenimiento de tipos de crédito. Aun así, items y customers se aceptan como campos opcionales para poder cargarlos de una sola vez cuando convenga.
Contexto de uso
Trigger
Dos Pinos (DP): se crea, modifica o inactiva un tipo de crédito y se envía a LDCOM para que quede disponible en el punto de venta.

Reglas y validaciones
Reglas de negocio
El creditTypeExternalId es obligatorio y es el código del tipo de crédito en el sistema de origen. LDCOM lo almacena para poder devolverlo en cada factura financiada.

items y customers son opcionales. El flujo normal es crear el tipo de crédito sin ellos y asociarlos después desde el mantenimiento.

Los plazos no son un tope ni un rango abierto: se envía el conjunto cerrado de plazos que el cajero podrá elegir en la venta (termsInWeeks). Es el único de los tres conjuntos que sí es requerido, porque sin plazos no se puede calcular la cuota.

customers solo se acepta cuando appliesTo = SPECIFIC_CUSTOMERS. Con los otros valores el plan aplica por clasificación y debe omitirse o enviarse vacío. Al revés sí se permite: un plan de clientes específicos puede crearse sin clientes.

Los tipos de crédito no se eliminan, se inactivan (active = false).

Cada factura puede estar asociada a un solo tipo de crédito. No se permite combinar artículos de tipos de crédito distintos en una misma transacción. Esta validación es de Facturación, no de este endpoint.

Modo asíncrono
Por defecto el llamado es síncrono: se procesa el lote completo y se devuelve el resultado.
Agregando el parámetro ?async=true el lote se acepta y se procesa en segundo plano, respondiendo 202 de inmediato con la cantidad recibida. Es la opción para lotes grandes, donde esperar el procesamiento completo puede agotar el tiempo de espera del cliente.
El 202 confirma que el lote se recibió, no que se guardó. Si un registro falla, el rechazo queda en la bitácora interna de LDCOM y hoy no hay forma de consultarlo desde afuera: hay que solicitarlo a Logical Data. Para lotes donde importe saber qué entró y qué no, usar el modo síncrono.
Resolución de artículos y clientes
Este endpoint no requiere mapeo previo en el Catálogo de Interfaces para artículos ni para clientes. La validación se hace contra LDCOM directamente.
Campo en request
 | Cómo se resuelve
 | 
items[].itemExternalId
 | Si un artículo no existe se rechaza con ITEM_NOT_FOUND.
 | 
customers[].customerExternalId
 | LDCOM confirma que el cliente exista antes de grabar; si no existe, o si el código no es numérico, se rechaza con CUSTOMER_NOT_FOUND.
 | 
Enviar siempre el código con el que Dos Pinos identifica el artículo o el cliente. No hace falta coordinar previamente ninguna configuración de catálogo para poder usar este endpoint.
Idempotencia
Si se recibe un creditTypeExternalId ya registrado en LDCOM, no se crea un duplicado: se actualiza el tipo de crédito existente con los datos recibidos. La respuesta lo refleja con wasCreated: true en las altas y wasCreated: false en las actualizaciones, dentro de creditTypes[].
Los plazos (termsInWeeks) se reemplazan por completo con los que vengan en el envío: siempre se manda la lista entera como debe quedar.
Vigencia
startDate y endDate son opcionales. Si no se envían (campo ausente, null o vacío) el tipo de crédito queda vigente sin límite: inicio 1900-01-01T00:00:00 y fin 2099-12-31T23:59:59. Si se envían, se graban tal cual.
Los valores por defecto son fijos: reenviar el mismo tipo de crédito sin fechas deja siempre el mismo resultado.

Al actualizar un tipo de crédito, las fechas se graban con lo que traiga el envío, o con los valores por defecto si no las trae.

La respuesta devuelve las fechas que quedaron grabadas.

Funcionalidades excluidas
Administración de artículos y clientes del tipo de crédito: asociar y desasociar artículos y clientes es trabajo del mantenimiento de tipos de crédito. Este endpoint los acepta como campos opcionales para una carga inicial, pero no ofrece operaciones parciales de agregar o quitar.

Consulta del resultado de un lote asíncrono: no existe un endpoint de estado. El resultado del procesamiento en segundo plano solo queda en la bitácora interna de LDCOM.

Bitácora de cambios: el histórico de creación, modificación e inactivación de tipos de crédito no forma parte de este endpoint.

Cálculo de la tabla de amortización: LDCOM la calcula en el punto de venta como simulación, a partir de la tasa y el plazo almacenados. El cálculo real es del sistema de crédito. No se envía ni se almacena por este endpoint.

Límite de crédito y clasificación banca / no banca del cliente: llegan por la interfaz de datos maestros de clientes, no por acá.

Indicador de subdocumento de financiamiento: la marca que distingue los créditos generados por un tipo de crédito se configura en el mantenimiento de subdocumentos.

Consulta y borrado de tipos de crédito: este endpoint solo registra y actualiza. No hay GET ni DELETE.

Códigos de error
Los rechazos son por registro, no del llamado completo. El detalle viene en errors.failures[] (índice que ocupaba en la lista enviada, código externo y motivo) cuando no entra ninguno del lote (500); si al menos uno entra, la respuesta es 200 y los rechazados quedan en la bitácora interna de LDCOM.

Response
200 OK — al menos uno del lote entró
Devuelve processedCount (cuántos entraron de verdad) y creditTypes[] con el tipo de crédito completo tal como quedó grabado — los mismos campos del request, más creditTypeId (el interno de LDCOM) y wasCreated, que sí genera el servidor. items/customers solo aparecen si se enviaron. Si el tipo de crédito se envió sin fechas, startDate y endDate vienen con los valores por defecto (1900-01-01T00:00:00 y 2099-12-31T23:59:59).
Un registro que falla no aborta el lote, pero tampoco aparece acá. Si mandás 3 y uno falla, processedCount es 2 y creditTypes[] trae solo esos 2 — el que falló no tiene ni índice ni motivo visible por esta vía, queda únicamente en la bitácora interna de LDCOM.
wide760json202 Accepted — modo asíncrono (?async=true)
El lote se aceptó y se encoló para procesar en segundo plano. received es cuántos se recibieron, no cuántos se guardaron — no hay forma de consultar el resultado después por esta vía.
wide760json400 Bad Request
Tres casos posibles: la lista vino vacía, algún campo no pasó la validación de forma ([Required]/[MaxLength]), o una fecha no viene en ISO 8601. Se rechaza antes de llegar a las reglas de negocio.
wide760jsonwide760json500 Internal Server Error — EXTERNAL_SYSTEM_ERROR, ninguno del lote entró
Si todos los registros del lote fallan, no hay nada que devolver en 200 con una lista vacía silenciosa — se trata como una falla del lote completo. Acá sí vienen los motivos, dentro de errors.failures[], con index, creditTypeExternalId, code y message.

Notas de implementación
Enviar siempre la lista completa de plazos como debe quedar: se reemplaza por completo.

Un mismo lote puede mezclar altas y actualizaciones: cada elemento de creditTypes[] trae su propio wasCreated.

Para retirar un tipo de crédito se envía active = false. No hay borrado.

Fechas, cuando se envían, en ISO 8601: con hora y timezone UTC (2026-09-01T00:00:00Z, recomendado) o solo la fecha (2026-09-01, se toma la medianoche). Un formato distinto (p. ej. 01/09/2026) se rechaza con 400.
