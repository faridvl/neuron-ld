PROPUESTA DE SOLUCIÓN
Servicios de Informática Lexington S.A. ofrece a Cooperativa De Productores De Leche Dos Pinos, R.L. la presente propuesta de solución para la creación de un componente base de integraciones, enfocado inicialmente en la gestión de datos maestros que LDCOM debe solicitar de forma diaria a Dos Pintos.
PRIMERA: DESCRIPCIÓN DE LOS REQUERIMIENTOS
SITUACIÓN ACTUAL 
Actualmente no existe un mecanismo centralizado y parametrizable que permita la comunicación entre sistemas Dos Pinos y LDCOM, gestionar frecuencias de sincronización de forma independiente o monitorear el flujo de datos en tiempo real.
SOLUCIÓN REQUERIDA 
Se requiere el desarrollo de una capa de integración (API) y mantenimientos de configuración en LDCOM para que sirva de base en estas y demás interfaces. Este API debe permitir la gestión de interfaces, la configuración de catálogos con equivalencias entre sistemas, la configuración de frecuencia para sincronizar datos maestros y un monitor para asegurar la consistencia de los datos.

PROPUESTA DE SOLUCIÓN TÉCNICA
1. API LDCOM
Se desarrollará un REST API intermediario entre LDCOM y Dos Pinos, que también tendrá el monitoreo de eventos, configuración de catálogos y flujos de sincronización de datos maestros.
Objetivo: establecer una plataforma base, centralizada y estandarizada que facilite todas las comunicaciones e integraciones entre el LDCOM y los sistemas de Dos Pinos.

Funcionalidades generales:
Abstracción y Estandarización: El API será el puente de comunicación entre LDCOM y las interfaces Dos Pinos, permitiendo intercambiar información de forma clara, segura y sin depender de los detalles internos de cada sistema.

API REST: El API proveerá el acceso a todos los endpoints requeridos por las futuras integraciones para obtener información de LDCOM.

Bitácora de eventos: El API llevará un registro automático de cada evento que pase através del API, el cual permite dar un monitoreo en tiempo real (Véase cambio 4 https://logicaldata.atlassian.net/wiki/spaces/DP/pages/134250511/Datos+Maestros+Propuesta+Soluci+n+CO-696-0021+API+LDCOM+y+sincronizaci+n+de+datos+maestros#4.-Monitor-de-Eventos)

Sincronización de Datos Maestros: El API se conectará a las interfaces de datos maestros para sincronizar la información automáticamente, según las reglas de ejecución configuradas (Véase cambio 5 https://logicaldata.atlassian.net/wiki/spaces/DP/pages/134250511/Datos+Maestros+Propuesta+Soluci+n+CO-696-0021+API+LDCOM+y+sincronizaci+n+de+datos+maestros#5.-Sincronizaci%C3%B3n-de-Datos-Maestros).

Reintentos de Sincronización: El API ejecutará reintentos de eventos que no fueron exitosos, según la pólitica de reintentos parametrizada para cada interface (Véase cambio 2 https://logicaldata.atlassian.net/wiki/spaces/DP/pages/134250511/Datos+Maestros+Propuesta+Soluci+n+CO-696-0021+API+LDCOM+y+sincronizaci+n+de+datos+maestros#Ejemplo-de-configuraci%C3%B3n-por-dato-maestro).

Objetivo: Centralizar las configuraciones necesarias para el acceso al API de Dos Pinos y la sincronización automatizada de Datos Maestros.

Ubicación: Se integrará en LDCOM en una ruta por definir.

Funcionalidades:

Opción para ejecutar manualmente la sincronización de cada uno de los catálogos de datos maestros.

3. Mantenimiento de Catálogos de Interfaces
Se contará con un módulo centralizado y configurable que permitirá mapear y traducir datos entre los sistemas externos (SAP, Oracle, SFA, etc.) y LDCOM.
Objetivo: Homologar IDs entre sistemas. Por ejemplo, si Dos Pinos identifica un tipo de cliente Distribuidor con el código distro-01, y LDCOM identifica ese mismo tipo de cliente con el ID 1, el API de LDCOM utilizará este catálogo de interfaces para realizar la conversión automática en cada transacción, en ambas vías.

Ubicación: Se integrará en LDCOM en una ruta por definir.

Funcionalidad: 
El usuario podrá seleccionar entre los distintos catálogos de LDCOM que participen en los procesos con las interfaces (ej. Monedas, Tipos de Cliente, Sucursales). 

Al seleccionar el catálogo a mapear, el sistema cargará un listado con los valores actuales registrados en LDCOM para ese catálogo.

Por cada valor, se contará con un campo editable donde podrá asignarle su correspondiente "ID Externo" con el que se reconoce el registro dentro de la interfaz. 

Cada catálogo puede definir, de forma opcional, un valor por defecto para usarse cuando un dato no esté homologado.
Ej., se podrá crear una “Marca” genérica y definirla como valor “por defecto” en el catálogo de interfaces. De este modo todos los artículos que no tengan una “marca” asociada en datos maestros quedaría asociado a esta marca genérica.


Si un catálogo no tiene un valor por defecto parametrizado, generará un error al sincronizar datos si su homologación no está configurada en el catálogo.
Ej., será posible parametrizar el catálogo de monedas sin indicar ningún valor por defecto, homologando únicamente los registros del catálogo.
Si una sincronización requiere recibir el código de moneda, será necesario que el código esté homologado en el catálogo de interfaces para que la sincronización sea exitosa

En caso de recibir un código de moneda no homologado, la sincronización será fallida.



El acceso a este mantenimiento estará restringido mediante permisos de usuario configurables en LDCOM.

4. Monitor de Eventos
Se desarrollará un monitor de eventos, el cual permitirá visualizar el estado de todos los eventos que pasan a través del API de LDCOM al recibir o enviar datos al API Dos Pinos. Este monitor tendrá los eventos de todas las interfaces en este proyecto y las interfaces futuras a desarrollar.
Objetivo: brindar trazabilidad total, diagnóstico de errores y control operativo sobre todo el flujo de datos relacionado a las integraciones de interfaces entre LDCOM y Dos Pinos.

Ubicación: Se integrará en LDCOM en una ruta por definir.

Funcionalidad: 
El usuario podrá visualizar desde el monitor y de forma detallada cada evento que ocurra en las interfaces, permitiendo visualizar información clave tales como:
Evento: Nombre de la acción realizada (ej. sincronización de materiales o notificación de preventa).

Origen y Destino: Identificación de qué componente envió la información y quién la recibió.

Fecha y Hora: Registro exacto del momento de ejecución del evento.

Contador de intentos: Visualización de cuántas veces el componente ha tratado de procesar el evento.

Estado: Visualización clara que indique si el evento fue exitoso o si presentó un error.

Detalle del evento: Una consulta de "detalle" para mostrar la respuesta completa recibida o enviada al momento de ejecutarse el evento, sea exitosa o fallida.

Usuario/servicio: Nombre del usuario o servicio que inició el proceso, sea automático, ejecutado manualmente o mediante el API de LDCOM.


El monitor permitirá al usuario ejecutar acciones tales como:
Búsqueda y filtrado: Consulta y filtrado de los eventos para mostrar en el monitor los eventos requeridos. Filtros disponibles:
Fecha inicial y final

Estado

Origen

Tipo de evento (Ej., Sincronización de proveedores, Preventa de granel nueva, etc.) 


Exportación de eventos: Opción para que el usuario pueda exportar a formato Excel el listado de eventos consultado.


Periodicidad de los datos:
Al ser una tabla con muchos eventos transaccionales, y para preservar el rendimiento del sistema, se almacenarán solo los eventos de los últimos 90 días según lo requerido por Dos Pinos para resguardo de auditoría. En el monitor solo se podrán ver, filtrar o exportar eventos con fecha no mayor a 90 días.

Cualquier evento mayor a 90 días se eliminará de la tabla y ya no será posible consultar en el monitor. 


El acceso a este monitor estará restringido mediante permisos de usuario configurables en LDCOM


5. Sincronización de Datos Maestros
Se desarrollarán los flujos de sincronización para insertar o actualizar en LDCOM los catálogos de datos maestros obtenidos desde el API de Dos Pinos. 
Objetivo: Sincronizar de forma automatizada los catálogos de datos maestros en LDCOM con los catálogos de Dos Pinos.

Ubicación: Los flujos se ejecutarán automáticamente, según las políticas de sincronización, dentro del API de LDCOM. 

Funcionalidad:
Por cada registro consultado en el API de Dos Pinos se creará o actualizará el registro en LDCOM si cumple las validaciones para procesar el registro.

En caso de uno o más registros no cumplan con las validaciones, el registro no será procesado y se registrará un error en la bitácora del componente.

Los registros válidos no existentes en LDCOM serán creados en el catálogo correspondiente. 

Los registros válidos existentes en LDCOM serán actualizados en el catálogo correspondiente.

El proceso de sincronización es individual por cada catálogo y se ejecuta según la frecuencia parametrizada en la configuración del API (Véase cambio 2. Configuración de APIs Dos Pinos).

Cada proceso de sincronización se va a reintentar según la política de reintentos definida en la configuración del API (Véase cambio 2. Configuración de APIs Dos Pinos).


Consideraciones
Para sincronizar los datos maestros se necesitan todos los catálogos de LDCOM correctamente creados en la carga inicial. Este proceso se realiza en la fase de implementación.

Una vez creados todos los catálogos, su homologación debe ser parametrizada en el catálogo de interfaces para que la sincronización sea efectiva (Véase cambio 3. Mantenimiento de Catálogos de Interfaces).

Se recomienda que los endpoints para obtener los catálogos de Dos Pinos tengan parámetros para filtrar por una fecha de modificación y de paginación de resultados. De este modo, al sincronizar cada día, no se tienen que traer todos los registros por completo sino solo los modificados y poder flexibilizar la consulta mediante páginas en caso de que lleguen a ser muchos datos.

Aunque en LDCOM se pueden modificar los datos maestros (si el usuario tuviese los permisos suficientes), la sincronización de datos maestros va a reemplazar todos los valores cada vez que se ejecuta el proceso. Ejemplo: Si se modifica manualmente en LDCOM el nombre del cliente con el código 123, este será reemplazado al siguiente día con el valor que tenga el catálogo de Dos Pinos. Lo mismo aplica para todos los valores de todos los datos maestros acá mencionados.

6. Integración al Monitor 360
Se desarrollará una integración al Monitor 360 de Dos Pinos para la notificación de errores durante el envío o recibo de datos por parte del componente de integración LDCOM.
Objetivo: asegurar que cualquier fallo que ocurra en los procesos de interfaz quede debidamente registrado en los sistemas de supervisión de Dos Pinos.

Ubicación: El API de LDCOM será el encargado de comunicarse con el Monitor 360 para la correspondiente notificación siempre que se detecte un registro de fallo. 

Funcionalidad: 
Cuando ocurre un evento (exitoso o fallido) en cualquier proceso de envío o solicitud de datos de alguna de las interfaces, el API LDCOM deberá enviar una notificación al Monitor 360 según su política de notificación.

Cada interfaz tendrá su propia política de notificación que será parametrizada en la configuración del API en LDCOM, para definir si se envían notificaciones fallida, exitosas o ambas. (Véase cambio 2 Configuración de APIs Dos Pinos)

Se utilizará el código de interfaz brindado por Dos Pinos y parametrizado en la configuración del API en LDCOM (Véase cambio 2 Configuración de APIs Dos Pinos)

Si el API LDCOM no es capaz de comunicarse con el Monitor 360, se deberá enviar un correo electrónico de notificación a las cuentas de correo parametrizadas en LDCOM. (Véase cambio 2 Configuración de APIs Dos Pinos)


SUPUESTOS Y RESTRICCIONES
Alcance de Interfaces Dos Pintos: Esta oferta incluye en el alcance únicamente las interfaces de catálogos maestros (POS-01, POS-02, POS-03, POS-04). La interface de CECOs no tiene código definido previamente. Las demás interfaces se consideran para fases posteriores.

Sesiones para certificación de integración: Se deberán coordinar sesiones de certificación para validar el flujo completo de sincronización de datos maestros. 

Reportes: Esta oferta no incluye en el alcance la creación de reportes en LDCOM. Lo que si se puede exportar es la bitácora de eventos de los últimos 30 días (Véase cambio 5. Monitor de Eventos)

Autenticación: Se asume que la autenticación con el API de Dos Pinos se realiza mediante un API Key, enviado en algún encabezado o parámetro del request. Este API Key será parametrizable desde LDCOM (si se cuenta con los permisos necesarios) y se guardará de forma segura. Si durante el desarrollo se define otra forma de autenticación, podría quedar sujeto a cambios de alcance en esta oferta.

Infraestructura
Se asume en esta oferta que todas las integraciones hacia Dos Pinos van a un API con el mismo dominio y autenticado de la misma forma (o sea, cada endpoint o interface comparte la misma URL base. Ej., https://api.dospinos.com/v1/…). Por tanto la configuración de la URL y el API Key es única para todas las interfaces (Véase cambio 2. Configuración de APIs Dos Pinos). Si durante el desarrollo se define algo distinto, podría quedar sujeto a cambios de alcance en esta oferta.

Se asume en esta oferta que existirá un ambiente de desarrollo y un ambiente de producción.
Dos Pinos brindará la documentación, llaves y accesos para conectarnos a cada ambiente.

El desarrollo y certificación de esta oferta y de las próximas integraciones se realizarán utilizando la conexión al ambiente de Desarrollo Dos Pinos.


La documentación de las interfaces se realizará mediante herramientas por definir, como Postman.


Desarrollo del API
Los flujos de sincronización en LDCOM se van a desarrollar hasta que Dos Pinos haya compartido los ambientes y la documentación de cada endpoint. Si durante esta fase, Dos Pinos desarrolla algo distinto a lo acordado, podría quedar sujeto a cambios de alcance en esta oferta.


Flujo de datos
Por razones de integridad de datos, los flujos de sincronización solo insertan o actualizan registros; No se pueden eliminar desde datos maestros. En LDCOM si se pueden eliminar manualmente los datos que no tengan transacciones relacionadas.

Se asume en esta oferta que el API de Dos Pinos brindará parámetros en los endpoints de catálogos grandes (como clientes, proveedores o artículos) para filtrar por fecha de modificación y paginación. Si los endpoints de Dos Pinos no pueden ofrecer estos parámetros la sincronización podría ser más lenta y saturar más los servicios. Si esto no es posible a la hora de integrarse, queda sujeto a cambios en el alcance de esta oferta.

Los contratos (conocidos como “schemas”) de cada endpoint aún no se han definido por parte de Dos Pinos e irán detallándose en el transcurso del proyecto. La cantidad de campos o endpoints podría variar. Sin embargo, si durante esta fase se cambia el desarrollo de forma que involucre un aumento significativo en el alcance, como cambios en la parametrización, creación de catálogos nuevos, o cambios significativos en los “contratos de cada endpoint” una vez se esté implementando, podría quedar sujeto a cambios en esta oferta.
