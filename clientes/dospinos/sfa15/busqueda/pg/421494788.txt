Descripción
Este documento cubre dos temas transversales a todos los endpoints LD-xx de la API de integración: cómo autenticarse, y cómo interpretar las respuestas de error. Ambos aplican de la misma forma sin importar el endpoint que se consuma.
1. Autenticación
Todos los endpoints LD-xx requieren un token de acceso emitido por Microsoft Entra ID. La API no emite tokens ni administra credenciales: solo valida el JWT que el llamador presenta en cada request.
Alcance
Aplica a todos los endpoints de la API de integración. No existen endpoints anónimos en ambientes con autenticación habilitada.
Secuencia del flujo
El cliente solicita un token a Entra ID usando grant_type=client_credentials.

Entra ID valida las credenciales de la aplicación y emite un access_token (JWT).

El cliente invoca el endpoint LD-xx enviando el token en la cabecera Authorization.

La API valida firma, vigencia y audiencia del token.

Si el token es válido se ejecuta la operación; si no, se responde 401 o 403 y el intento queda registrado en auditoría.

Reglas de negocio
El token se solicita a Entra ID, no a LDCOM ni a esta API.

Se envía en cada request como Authorization: Bearer <access_token>.

La API acepta como audiencia válida tanto {ClientId} como api://{ClientId} de la aplicación que representa a la API. Ambas formas corresponden al mismo registro; la que emite Entra ID depende de cómo el llamador pida el scope.

Se recomienda cachear el token y renovarlo con margen antes del vencimiento. Un token que expira a mitad de vuelo produce un 401.

Auditoría de accesos rechazados
Los intentos fallidos quedan registrados en la tabla Events:

textwide760Notas de implementación
La validación usa Microsoft.Identity.Web sobre el esquema JwtBearer.

La auditoría de accesos rechazados se engancha a los eventos existentes de JwtBearer sin reemplazarlos, para no perder el comportamiento por defecto.

Un fallo al auditar nunca convierte un 401/403 limpio en un 500: se registra en el log y la respuesta original se mantiene.

Swagger (solo en Development) incluye el esquema Bearer para probar los endpoints con un token pegado a mano.

2. Manejo de errores
Todas las respuestas de error del API — fuera de los 401/403 de autenticación, que emite el middleware de Entra ID sin pasar por este envelope — usan el mismo formato:
jsonwide760Campos del envelope
Campo
 | Tipo
 | Descripción
 | 
status
 | integer
 | Código HTTP, repetido en el cuerpo.
 | 
code
 | string
 | Código de error estable. Es el valor a usar para tomar decisiones automáticas, no el message.
 | 
message
 | string
 | Mensaje descriptivo en español, orientado a operación.
 | 
data
 | null
 | Siempre null en respuestas de error.
 | 
errors
 | object | null
 | Detalle estructurado del rechazo. La forma depende del code (por ejemplo catalog/externalValue, o field/value/validValues).
 | 
401 / 403 no usan este envelope
Los códigos 401 (token ausente, inválido o expirado) y 403 (token válido pero sin el scope requerido) los emite el middleware de autenticación directamente — no pasan por este formato. Ver la sección de Autenticación arriba para el detalle de auditoría de estos casos.
