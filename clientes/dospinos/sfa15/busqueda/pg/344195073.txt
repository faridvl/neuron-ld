Descripción
Crea una nueva preventa en LDCOM. El identificador del documento es generado por LDCOM y retornado en el response.
La preventa queda en estado PENDING y disponible para ser facturada desde el módulo de Facturación de LDCOM. El cajero no puede editarla — solo facturarla o anularla.

Triggers
B2C: Nuevo pedido recibido en apps externas (Uber Eats, ecommerce, etc.). La preventa se crea automáticamente y se despacha desde la sucursal correspondiente usando el módulo de Facturación.

SAP / Asociados: Preventas con factura para cobro de comisiones (código 6000), originadas en SAP.

Reglas y validaciones
Reglas de negocio
El preorderId es generado por LDCOM. No se acepta desde el request.

Estado inicial: PENDING.

isEditable por defecto: false. En preventas B2C el cajero solo puede facturar, no editar.

Los artículos deben existir en LDCOM (itemExternalId).

El cliente, autorizados y finca deben existir en LDCOM por su externalId.

No se validan saldos de crédito al crear la preventa (esa validación ocurre en la facturación).

Validación de montos (por artículo)
LDCOM valida que los montos enviados sean consistentes. El cliente es responsable de calcularlos correctamente. LDCOM no recalcula ni sobrescribe los montos recibidos — los persiste tal cual si pasan la validación.
Fórmulas validadas:
wide760Nota sobre impuestos: El caller envía unitTaxPercentage como número (ej. 13). LDCOM resuelve internamente el ID de impuesto correspondiente. Si el porcentaje no coincide con ningún impuesto configurado, se retorna INVALID_TAX_PERCENTAGE.
Nota sobre redondeo: Se acepta una diferencia de hasta ±0.01 por ítem para absorber diferencias de redondeo entre sistemas. Diferencias mayores retornan INVALID_AMOUNT_CALCULATION.

Idempotencia
Si se recibe un request con un ecommerceReferenceNumber que ya existe en LDCOM, no se crea un duplicado. Se retorna el registro existente con HTTP 200.
Efectos secundarios
Crear una preventa para un asociado con un documento de crédito (o de financiamiento) incrementa su saldo acumulado de preventas en LDCOM.

Campos excluidos
Las siguientes campos existen en una preventa de LDCOM pero no se exponen en este endpoint por estar fuera del scope de integración actual:
Bodega y caja específica: Se obtienen automáticamente.

Estado manual de la preventa: Toda preventa se crea en estado PENDING.

Descuentos desde catálogo: Los descuentos son creados en LDCOM, pero en el API no se necesita especificar el ID desde el catálogo, sino solo el monto calculado en el request.

Impuesto desde catálogo: Los impuestos son creados en LDCOM, pero en el API no se necesita especificar el ID desde el catálogo, sino solo el porcentaje. Si el impuesto con ese porcentaje no está configurado en LDCOM se retornará un error.

Cierre de caja: Toda preventa y factura deben asociarse a un ID de cierre. Las preventas creadas desde el API se asocian a un cierre creado automáticamente cada día.

Usuario / Vendedor: Las preventas creadas desde el API se asocian a un usuario de sistema.

Funcionalidades excluidas
Las siguientes funcionalidades relacionadas a preventas existen en LDCOM pero no se exponen en este endpoint para simplificar el alcance del API, al ser más relevantes del módulo de facturación:
Promociones / "item groups": Son promociones que se activan al escanear artículos.

Gasto unitario / venta extraordinaria: Son funcionalidades relacionadas a las compras de proveedores.

Servicios: Es un catálogo de servicios asociados a la factura.

Venta cruzada: Son artículos sugeridos desde el módulo de facturación.

Plan lealtad: Las relaciones de clientes con su plan de lealtad es una funcionalidad del módulo de facturación.

Pendiente de entrega: Es un campo relacionado al módulo de rutas de LDCOM.

Afiliado / Ubicación / Operación: Son campos relacionados a otros módulos y procesos internos de LDCOM.

Factor unitario: Se utiliza para describir artículos "sueltos" (ej. una caja de pastillas de 12 tiene un factor unitario de 12).

Notas de implementación
Todos los montos son number con precisión de 2 decimales. No usar string.

Fechas siempre en ISO 8601 con timezone UTC (Z).

Los catálogos deben coordinarse con el equipo de LDCOM durante la configuración inicial en el Catálogo de Interfaces.

Para flujos B2C, siempre incluir customAttributes.ecommerceReferenceNumber para garantizar idempotencia ante reintentos de red.

Si se envían múltiples métodos de pago, la suma de payments[].totalPayableAmount debe igualar summary.totalAmount.
